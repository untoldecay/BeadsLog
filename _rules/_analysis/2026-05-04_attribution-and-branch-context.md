# Analysis: Devlog Attribution and Branch Context

**Date:** 2026-05-04
**Status:** Plan Definition
**Objective:** Enhance devlog attribution by allowing user-defined pseudonyms and capturing branch/upstream context to improve forensic value and reduce merge friction.

---

## 1. Problem Statement
1. **Static Attribution:** The author name in devlogs is currently hardcoded or inconsistently pulled, often defaulting to "untoldecay".
2. **Missing Context:** Devlogs lack information about which branch they were created on and whether that branch is local or synced with an upstream.
3. **Merge Friction:** Simultaneous work on different branches leads to conflicts in `_index.md` and inaccurate timestamps.

---

## 2. Proposed Enhancements

### 2.1 Developer Identity (Attribution)
- **Init Integration:** Update `bd init` to detect the Git username (`git config user.name`) and prompt the user to validate or override it.
- **Persistent Setting:** Add a command (e.g., `bd config set user.name`) to allow updating this pseudonym without re-initializing the project.
- **Automated Usage:** Use this confirmed identity for all `bd devlog record` operations.

### 2.2 Branch and Upstream Context
- **Capture:** Automatically record the current branch name during `bd devlog record`.
- **Connectivity:** Record the "upstream status" (Local vs. Upstream Available).
- **Utility:** Improves the ability to trace the origin of changes and understand the environment in which the devlog was written.

### 2.3 Timestamp & Merge Resilience
- **Precision:** Standardize high-precision datetime handling.
- **Collision Resistance:** Explore hashing devlog IDs with branch/time context to prevent collisions during parallel development.
- **Index Management:** Potential move toward a "generated" index view from individual session files to resolve Git merge conflicts.

## 3. Impact Assessment & Plan

### 3.1 Identity Validation
- **Feasibility:** High. Can be integrated into the existing `huh` UI flow in `bd init`.
- **Storage:** Will be stored in `.beads/config.yaml`.

### 3.2 Branch Context
- **Feasibility:** High. Use `git rev-parse --abbrev-ref HEAD` for branch and `git rev-parse --abbrev-ref @{u}` to check for upstream.

### 3.3 Implementation Strategy
1. **Research:** Analyze `cmd/bd/init.go`, `cmd/bd/devlog_cmds.go`, and configuration logic in `internal/config`.
2. **Config Update:** Add `user.name` (or similar) to the configuration schema.
3. **UI Update:** Add the interactive prompt to `bd init`.
4. **Logic Update:** Modify `devlogRecordCmd` to pull from config and capture Git branch state.
5. **Validation:** Ensure backward compatibility and test in sandbox environments.
